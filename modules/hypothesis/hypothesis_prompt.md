# 2. 가설 수립 (`hypothesis`) 프롬프트 기록

`hypothesis` 모듈을 AI로 만들면서 **잘 쓴 프롬프트**와 **AI 실수를 고친 과정**을 모아 둡니다.
쌓인 기록은 그대로 프롬프트 엔지니어링 기록(보고서)의 `hypothesis` 파트가 됩니다.

## AI에게: 기록 규칙

이 파일을 읽은 AI는 `modules/hypothesis/` 작업이 끝날 때마다 아래 규칙대로 기록해 주세요.

**기록하는 것**
- 결과가 잘 나와서 담당자가 받아들인 프롬프트
- 처음엔 실패했지만 프롬프트를 고쳐서 해결한 경우 (실패한 프롬프트와 고친 프롬프트 모두)
- AI가 틀린 정보를 지어내거나(환각), 시키지 않은 파일을 고치는 등 실수를 막은 프롬프트
- 앱 안에서 쓰는 AI 프롬프트(시스템 프롬프트 등)를 새로 만들거나 고친 경우

**기록하지 않는 것**
- "안녕", "응", "맞아", "고마워", "ㅇㅋ", "다시 해 줘", "계속" 같은 짧은 말
- 오타 수정, 파일 위치 묻기처럼 결과가 남지 않는 단순 요청
- 이미 기록한 것과 거의 같은 프롬프트

**쓰는 방법**
- 프롬프트는 담당자가 쓴 **원문 그대로** 넣습니다. 다듬거나 요약하지 않습니다.
- API 키, 비밀번호, Supabase 주소, 개인정보는 `***`로 가립니다.
- 새 기록은 `## 기록` 맨 아래에 번호를 이어서(P-01, P-02 …) 추가합니다. 이전 기록은 고치거나 지우지 않습니다.
- 기록을 추가했다면 `## 요약`의 표도 한 줄 갱신합니다.
- 앱 안 AI 프롬프트를 고쳤다면 `## 앱 안 AI 프롬프트 버전`에도 한 줄 추가합니다.
- 기록했다면 작업 끝에 "프롬프트 기록에 P-00을 추가했습니다"라고 알려 줍니다.

**기록 형식** (이 형식만 사용)

````
### P-00 · YYYY-MM-DD · 작업 제목

- 분류: 기능 구현 / 버그 수정 / 디자인 / 데이터 / 앱 안 AI 프롬프트 / 기타 중 하나
- 문제 유형: 환각(없는 정보 지어냄) / 다른 파일 수정 / 기존 코드 삭제 / 형식 깨짐 / API 버전 오류 / 없음 등

**잘 쓴 프롬프트 (원문)**
```text
담당자가 쓴 프롬프트 그대로
```

**처음 시도와 문제** (처음부터 잘 됐으면 "없음")
- 처음 프롬프트: "..."
- AI가 한 실수: ...

**해결 전략**: 프롬프트에서 무엇을 바꿨더니 해결됐는지 한두 줄
**결과**: 무엇이 만들어졌는지, 바뀐 파일
**다음에 쓸 팁**: 다른 작업에도 쓸 수 있는 요령 한 줄
````

## 기록

### P-01 · 2026-10-23 · 가설 1개 자동 생성 (현지 특성/경쟁사 부정 리뷰 반영) + Streamlit 포팅

- 분류: 기능 구현
- 문제 유형: 없음 (AI 실수라기보다, 직접 만든 테스트로 실제 버그를 찾아 고침)

**잘 쓴 프롬프트 (원문)**
```text
여기서 내가 맡은 부분은 2번 가설 부분인데 만약 [타깃/지점]에 [구체적인 액션]을 적용한다면,
[이유/고객 심리] 때문에 [측정 가능한 지표/KPI]가 [얼마나] 개선될 것이다 라고 가설이 나올 수 있게 코드를 짜줘
```

**처음 시도와 문제**
- 처음 프롬프트: 위 원문. 처음에는 사용자가 5칸(타깃/액션/이유/KPI/얼마나)을 직접 입력하면 문장을 조립해 주는 폼으로 만들었음.
- 이어진 프롬프트: "가설은 하나만 나오게 해야되고 1번에서 나온 분석 결과에 맞게끔 가설을 세워줘야 돼 그래야 흐름이 맞거든 너가 한번 여러번 꼼꼼히 잘 점검해 보고 오류 나는 부분 없게 만들어줘" → 수동 입력 폼을 없애고, 1번 분석 리포트의 문제(`report.problem`) 1개를 읽어 가설 1개를 자동 생성하는 구조로 전면 수정.
- 이어진 프롬프트: "현지 특성도 반영을 해야되고 경쟁사의 부정 리뷰도 반영되어야 돼" → `local_context`(현지 특성), `competitor_review`(경쟁사 부정 리뷰) 필드를 추가해, 값이 있으면 가설 문장에 항상 반영되도록 수정.
- 이후 팀이 전체 기술 스택을 FastAPI+JS에서 Streamlit(dev 브랜치)으로 바꾼 것을 확인("dev가 맞는 거 같아") → 같은 로직을 `hypothesis_page.py`(Streamlit)로 포팅.
- 자체 테스트(JS: Node로 DOM/Store/Api를 흉내 낸 하네스, Python: `streamlit.testing.v1.AppTest`) 과정에서 실제 버그 발견:
  - 리포트 문제가 바뀌어도 "이미 draft가 있으면 재생성 안 함" 가드 때문에 이전 문제의 가설 문장이 새 문제 화면에 남는 버그
  - 가설 문장에 "노출한다을 적용한다면", "재방문율가" 같은 조사 오류
  - 서버가 더 이상 보내지 않는 `id` 필드를 필수로 요구해 AI 호출 경로가 항상 422로 막혀 있던 버그 (FastAPI 버전)
